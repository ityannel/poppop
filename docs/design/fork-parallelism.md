# 設計メモ：Fork の並列化

状態：**検討中（実装しない）**

## いまの約束

仕様書の「評価の順序」と `Fork` の説明のとおり、`Fork` は、**分岐を宣言した順に評価して、結果を宣言した順の `List`（または `Dict`）で返します**。どれかの分岐が失敗したら、`Fork` 全体が失敗します。

## 並列化したい理由

`Fetch` を複数、同時に出して、待ち時間を重ねたい。

```
urls >> Fork {
    "https://a.example" >> Fetch.
    "https://b.example" >> Fetch.
}
```

## 崩れるもの

| 約束 | 並列にすると |
|---|---|
| **評価の順序**（左から右） | 分岐の中の外部効果（`Display`、`Sleep`、`Fetch`、`WriteFile`、`Input`、`Random`）の順番が、決まらなくなる |
| **出力の再現性** | 同じプログラムで、`Display` の行の並びが、実行のたびに変わりうる |
| **`Input`** | 2 つの分岐が、同時に質問することになる |
| **`Random`** | 乱数を使う順序が変わり、同じ種でも、結果が変わる |
| **エラー** | 1 つの分岐の失敗のとき、ほかの分岐を、止めるのか、最後まで待つのか |

## Playground の事情

実行環境（Pyodide）は、1 つのスレッドです。並列にできるのは、`Fetch` や `Sleep` のような、**待っている間だけ**です（`asyncio` の協調動作）。計算を速くする効果は、ありません。

## 案

### 案 A：何もしない（いまのまま）

一番安全です。待ち時間が問題になった実例が、まだありません。

### 案 B：選んだときだけ、並列にする

```
urls >> Fork parallel {
    ...
}
```

規則の案：

1. 結果の順序は、いつでも、宣言順（約束は、変わらない）。
2. 並列の分岐の中で、**`Display`、`Input`、`WriteFile`、`Random`、`Sleep`** を使ったら、エラー（`RuntimeError`）にする。使ってよい外部効果は、`Fetch`、`PostFetch`、`HttpRequest` だけ。
3. どれかが失敗したら、ほかの分岐を、待たずに止め、最初のエラーを返す。

**崩れるもの**：`Fork` の書き方が増える（新しい書き方を、整形、色付け、拡張、仕様書に足す）。「使えない処理がある」ルールが、初心者には、分かりにくい。

### 案 C：別の名前の関数（`FetchAll`）

並列にしたいのは、ほぼ通信だけなので、`Fork` ではなく、`urls >> FetchAll` のように、**通信専用の標準関数**にする。`Fork` の約束は、まったく崩れない。

## 推奨

1. **いまは、実装しない。**
2. 待ち時間が問題になる、実際のプログラムが出てきたら、**案 C（`FetchAll`）を先に検討する。** `Fork` の約束を崩さないためです。
3. それでも足りないときだけ、案 B を、上の 3 つの規則つきで検討する。

## 決める前に答えるべきこと

* 実際に、待ち時間が問題になった例は、何か。
* 並列の同時数に、上限（たとえば 4）を持たせるか。
* 通信の失敗を、全体の失敗にするか、結果の中に入れるか。
