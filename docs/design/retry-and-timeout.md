# 設計メモ：Retry とタイムアウト

状態：**検討中（実装しない）**

## 困りごと

API や `Fetch` は、一時的に失敗することがあります（回線の切れ、混雑）。そのたびに、人が実行しなおすのは、面倒です。また、返事が来ない通信で、プログラムが止まってしまうのも困ります。

## いまの PopCorn で書けるか

書けます。`Loop` と `Try` / `Catch` を組み合わせます（仕様書の「やり直す」にも、同じ例があります）。

```
(0, null) >> Loop as (attempt, last) {
    last >> Break when last != null.           // 成功したら、その値で終わる
    null >> Break when attempt >= 3.           // 3 回失敗したら、あきらめる（null を返す）
    "https://example.com/api" >> Try {
        Fetch.
    } Catch {
        null.
    } >> response.
    (attempt + 1, response).
} >> result.
```

* `Loop` の状態は `(attempt, last)`（何回目か、直前の結果）。
* 成功したら（`last` が `null` でなければ）、その値で、`Break` して終わる。
* 3 回失敗したら、`null` を返して、あきらめる。

少し長く、書き間違えやすいのが、難点です。

## 案

### 案 A：`Retry` ブロックを足す

```
"https://example.com/api" >> Retry(3) as attempt {
    Fetch.
} >> response.
```

* ブロックが成功するまで、最大 3 回くり返す。3 回とも失敗したら、最後のエラーを、そのまま出す。
* `attempt` は、0 から数えた回数。

**崩れるもの**

* **新しい特殊形になる**。`language_meta.py` のブロックの一覧、字句解析、構文解析、評価、整形、色付け、VS Code 拡張、仕様書の記法を、全部直す必要がある（`Try` を足したときと同じ規模）。
* **やり直してよい失敗の範囲**が、決まっていない。`NetworkError` だけか。`TypeError` のようなプログラムの間違いまで、くり返したら、無駄に待つだけ。
* **副作用の二重実行**：`PostFetch` や `WriteFile` を、やり直すと、同じ書き込みが 2 回起きるかもしれない。
* **待ち時間**：やり直しの間隔（固定、だんだん長く）を決める必要がある。乱数を混ぜると、評価の再現性が下がる。

### 案 B：書き方の例を、仕様書に載せるだけ

新しい文法は足さず、「`Try` と `Loop` で、やり直す」書き方を、仕様書の例として載せる。

### タイムアウト

* **計算のタイムアウトは、Playground ではできません。** 実行環境（Pyodide）は、ブラウザの 1 つのスレッドで動くので、動いている同期の計算を、外から止められません。
* **待つ処理（`Fetch`、`Sleep`）のタイムアウトは、できます。** `Fetch` の補助引数や、`HttpRequest` の設定として、秒数を渡せるようにするのが、文法を増やさない形です。

## 推奨

1. **まず案 B**：書き方の例を、仕様書に載せる。
2. 同じ手書きが、**サンプルやレッスンで 2 回以上**出てきたら、案 A を実装する。そのときは、`NetworkError` だけをやり直す、回数の上限を必ず持つ、`PostFetch` と `WriteFile` は、やり直さない（または、明示したときだけ）、を最初の決まりにする。
3. タイムアウトは、`Fetch` と `HttpRequest` の設定として、別に検討する。

## 決める前に答えるべきこと

* 待ち時間を、言語の機能にするか、`Sleep` を、ブロックの中に書かせるか。
* `Retry` の中で `Display` した出力は、やり直しのたびに、出るのか。
